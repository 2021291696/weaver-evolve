# Codex 信息分层指南

## 核心原则

**不确定时下沉一级。** 全局污染会影响所有项目；项目层遗漏通常只影响一个范围。

## 规则与配置层级

| 范围 | 规则文件 | 配置文件 | 适合内容 |
|---|---|---|---|
| 全局 | `~/.codex/AGENTS.md` | `~/.codex/config.toml` | 跨项目硬规则、通用 Codex 配置 |
| 项目 | `<项目根>/AGENTS.md` | `<项目根>/.codex/config.toml` | 项目构建、测试、目录边界、项目配置 |
| 子目录 | `<子目录>/AGENTS.md` | 通常继承项目配置；仅在 Codex 明确支持且确有必要时另设 | 模块或子项目专属规则 |

`AGENTS.md` 是指令，不是历史档案。只写未来执行必须遵守、可操作且当前有效的规则。

## 全局层判定

可进入全局层的信号：

- 用户明确说“所有项目”“以后默认”“无论哪个仓库”；
- 跨项目一致的安全、提交、包管理或协作要求；
- Codex 全局行为配置，且配置项经过当前文档或现有配置验证。

不要放入全局层：具体仓库路径、一次性任务、单项目技术选型、未经验证的偏好推断。

## 项目与子目录层判定

- 只影响一个仓库：项目根 `AGENTS.md`。
- 只影响某模块、包或嵌套项目：该范围最近的 `AGENTS.md`。
- 子目录已有 `AGENTS.md` 时，先理解继承关系，再更新最具体的一层。
- 同一规则不要在父子层重复；子层只写补充或覆盖。

## 规则、配置、记忆与知识的区别

| 内容 | 去向 |
|---|---|
| 必须执行/禁止执行的指令 | `AGENTS.md` |
| Codex 可识别的配置键 | 对应作用域的 `config.toml` |
| 稳定偏好、项目决策、当前状态 | 项目已有 memory/docs；没有合适位置时先建议，不随意造体系 |
| 通用概念、规律、方法论 | 用户现有知识库，遵循其 `AGENTS.md` |
| 已验证错误、修复与证据 | 项目 `.codex/ERROR_LOG.md` |
| 技能程序性说明 | `~/.agents/skills` 或项目 `.agents/skills` |

## 边界案例

| 场景 | 判定 |
|---|---|
| “以后 Python 项目统一用 uv” | 全局规则，前提是用户确实指所有项目 |
| “这个仓库只允许改 `src/`” | 项目规则 |
| “前端包必须跑视觉回归” | 前端子目录规则，若只对该包生效 |
| “把模型设为 X” | 先确认作用域，再修改对应 `config.toml` |
| 某次构建失败的命令输出 | 错误日志或任务记录，不直接进入 `AGENTS.md` |
| 从两次对话推断用户偏好 | 标注推测并请求确认，不自动写规则 |

## 技能路径

- 个人技能：`~/.agents/skills/<skill-name>/SKILL.md`
- 项目技能：`<项目>/.agents/skills/<skill-name>/SKILL.md`
- 显式调用：`$skill-name`

路径不存在时，不因“可能有用”而创建空目录或占位技能。
